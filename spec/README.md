# spec 目錄規則

這裡放驅動開發的需求與設計文件。新增或修改 spec 前先讀這份。

2026-10-26 以前的需求和決定記在 [`docs/HANDOFF.md`](../docs/HANDOFF.md)，沒有補寫成 spec。

## 命名

```
yyyymmdd-<功能名>.md
```

- `yyyymmdd` 是 spec 第一次建立的日期，不是最後修改的日期。
- `<功能名>` 用簡短的英文 kebab-case，例如 `20261026-add-room-by-url.md`。

## 內容

用繁體中文寫。一份 spec 通常包含：

- **摘要**：要做什麼、為什麼。轉述 Leo 的需求，不直接引用原話，但要保留限定詞，例如「暫時」「預設」「盡量」。
- **設計**：分成幾節說清楚，例如行為、資料格式、指令介面、預設值。
- **驗證**：怎麼確認做對了。只能在 Leo 的 Mac 上測的項目（真實直播、抖音側欄）要標出來。
- **不在範圍內**：這次刻意不做的事。

大的工作先寫一份總 spec 定下共同規則和分期，每一期再各寫一份。

## 已提交的 spec 不改寫

spec 提交後，原本的內容不再改寫或刪除。需求之後變了，或新 spec 跟舊的衝突時：

- 在舊檔案最後**追加**一節 `## 更新：<說明>（yyyy-mm-dd）`，寫清楚改了什麼、為什麼；
- 或者寫一份新的 spec，在裡面註明它取代了哪一份。

當初決定了什麼要一直讀得到。

## 提交的內容只寫最後的決定

同一輪工作在提交前來回改需求很正常，但提交出去的 spec 只寫這一輪最後定下來的狀態，不留中間的反覆。

提交 spec 前：

- 把要提交的內容最後再讀一遍。
- 如果討論是 A → B → A，提交的文件讀起來要像只有 A。B 整個拿掉，不要留成「考慮過但沒採用」、刪除線或附註。
- 不要寫成「做 A，不做 B」「拿掉了 B」「改用 A 取代 B」，如果 B 只是提交前就被推翻的中間想法。它從來沒有真的存在過，留著只會讓之後的讀者多一件要排除的事。直接寫 A。
- 這條只管**同一輪、還沒提交**的反覆。已經提交過的決定後來被推翻，是真的歷史，照上一節的方式追加記錄，不要抹掉。

目標是之後任何人讀到已提交的 spec，看到的都是乾淨的決定，沒有過程中的雜訊。
